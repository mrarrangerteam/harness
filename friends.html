PART 1 · WHY (ทำไม)

ช่องว่างของ Harness (The harness gap)

โมเดล AI ตัวเดียวกันเป๊ะ แต่ใส่โครงสร้างต่างกัน ผลลัพธ์ห่างกันถึง 34%! การเลือก Harness คือการตัดสินขีดความสามารถ ไม่ใช่แค่เรื่องธีมสวยงาม

PART 2 · WHAT (คืออะไร)

Harness, Multiplexer, OS

นิยามที่ถูกต้อง, กายวิภาคของ Loop การทำงาน, และทัวร์ระบบชั้นนำระดับโลก ทั้งฝั่ง Frontier (เชิงพาณิชย์) และ Open Source

Roll Your Own (สร้างขึ้นเอง)

 ทำไมต้องเรียนรู้สิ่งนี้ (Why learn this)

คุณยอมจ่ายเงินอัปเกรดโมเดลตัวใหม่ล่าสุด...
แต่ทำไมงานที่คุณได้กลับไม่ได้เพิ่มขึ้นเป็น 2 เท่า?

ผลงานที่ได้ (Output)  =  เพดานของโมเดล (Model ceiling)  ×  ระยะเอื้อมของ Harness (Harness reach)

นี่คือ "ผลคูณ" (Product) ไม่ใช่ผลบวก! โมเดล AI เป็นตัวกำหนดว่าเพดานความฉลาดสูงสุดอยู่ตรงไหน แต่ Harness เป็นตัวกำหนดว่าคุณจะเอื้อมไปแตะเพดานนั้นได้กี่เปอร์เซ็นต์ ถ้าตัวคูณฝั่ง Harness ต่ำ โมเดลระดับเรือธงจะทำงานได้แย่พอๆ กับโมเดลปีที่แล้ว!

โมเดล (Model) คือสิ่งที่คุณ "เช่าเขาใช้"

คุณไม่ได้เป็นเจ้าของ ไม่สามารถเข้าไปคุมเนื้อในได้ และคู่แข่งทุกคนของคุณก็จ่ายเงินซื้อโมเดลตัวเดียวกับคุณได้ทันที

Harness คือสิ่งที่คุณ "เป็นเจ้าของและควบคุมได้"

กลยุทธ์จัดบริบท (Context), เครื่องมือ (Tools), สิทธิ์การรัน (Permissions), และระบบตรวจความถูกต้อง (Verification) นี่คือครึ่งหนึ่งที่ทำให้คุณสร้างความได้เปรียบแบบสะสม

หมายเหตุชี้แจง: ไม่มีผู้ให้บริการรายใดประกาศสมการนี้เป็นสูตรทางการ แต่นี่คือแบบจำลองความคิด (Mental Model) ที่มีข้อมูลตัวเลขจริงวัดผลรองรับในอีก 3 สไลด์ถัดไป

 ทำไมต้องเรียนรู้สิ่งนี้ (Why learn this)

3 ข้อสรุปที่เปลี่ยนวิธีคิดในการทำงาน

01

การเลือก Harness คือการตัดสินขีดความสามารถ

ไม่ใช่เรื่องความชอบส่วนตัวเรื่องธีมหรือปุ่มลัด มันมีมูลค่าเท่ากับคะแนนความสำเร็จของงานจริงหลักสิบเปอร์เซ็นต์ ซึ่งมากกว่าการอัปเกรดโมเดลส่วนใหญ่ด้วยซ้ำ

02

ทักษะ Harness ส่งต่อข้ามยุคได้ แต่ทักษะโมเดลไม่

ทริคพรอมต์ที่ปรับจูนมาเพื่อโมเดลรุ่นหนึ่ง พอโมเดลรุ่นใหม่ออกมาก็ใช้ไม่ได้แล้ว แต่วิธีการจัด Context, การคุม Permission, และการตรวจทานผลลัพธ์ ใช้ได้กับทุกโมเดลตลอดไป

03

คุณมักใช้งานสิ่งที่จ่ายเงินไปแล้วได้ไม่คุ้มค่า

ก่อนที่คุณจะตัดสินใจจ่ายเงินซื้อโมเดลที่แพงขึ้น ลองเช็คดูก่อนว่าโมเดลตัวเดิมที่คุณใช้อยู่ กำลังทำงานอยู่บน Harness ฝั่งที่ดึงคะแนนตกไป 34 แต้มหรือไม่

ความจริงที่หลายคนมองข้าม: ถ้ามีสองทีมวิศวกรที่ซื้อโมเดลเรือธงตัวเดียวกันเป๊ะ แต่ทีมหนึ่งส่งมอบงานได้มากกว่าอีกทีมถึง 2 เท่า... ความต่างไม่ได้อยู่ที่ตัวโมเดล แต่อยู่ที่ทุกเรื่องที่เรากำลังจะพูดถึงในสไลด์ชุดนี้!

 นิยามพื้นฐาน (What)

Harness คืออะไรกันแน่?

Harness คือ "โปรแกรม" ที่เปลี่ยนโมเดลทำนายข้อความ (Text-completion model) ให้กลายเป็น Agent (เอเจนต์ทำงานอัตโนมัติ)

มันทำหน้าที่ถือครอง 4 สิ่งสำคัญที่ตัวโมเดล AI เองไม่มีทางทำได้ด้วยตัวเอง:

  • วงลูป (The loop): การสั่งรันโมเดลซ้ำๆ ต่อเนื่องจนกว่างานจะเสร็จสิ้น
  • หน้าต่างข้อมูล (The window): การตัดสินใจว่าไฟล์ใดบ้างที่ควรนำเข้าไปให้โมเดลอ่าน
  • ขอบเขตความปลอดภัย (The boundary): สิทธิ์ในการอ่าน, เขียนไฟล์, และรันคำสั่ง bash ในเครื่อง
  • บันทึกประวัติ (The transcript): การเก็บรักษาความทรงจำของการสนทนา และบีบอัดเมื่อข้อมูลเริ่มล้น
เปรียบเทียบให้เห็นภาพสำหรับมือใหม่: โมเดล AI เปรียบเหมือน "เครื่องยนต์ทรงพลัง" แต่ตัวมันเองวิ่งไปไหนไม่ได้... ส่วน Harness คือ "โครงรถยนต์ คันเร่ง พวงมาลัย เบรก และถังน้ำมัน" ที่ประกอบเข้าด้วยกันจนกลายเป็นรถที่ขับไปถึงจุดหมายได้จริง!
โมเดล (THE MODEL)

ฟังก์ชันไร้สถานะ (Stateless function): รับข้อความก้อนหนึ่งเข้ามา แล้วเดาคำถัดไปที่น่าจะใช่ที่สุดออกมา จบแค่นั้น ไม่มีความจำ ไม่มีการลงมือทำ

HARNESS

โปรเซสที่มีสถานะ (Stateful process): มีลูป, สิทธิ์เข้าถึงเครื่อง, ปลั๊กอินเครื่องมือ, ระบบตรวจสอบผล, และพื้นที่จัดเก็บประวัติการทำงาน

 ส่วนประกอบภายใน (What)

6 ชิ้นส่วนสำคัญ และทุก Harness วางเดิมพันในแต่ละชิ้นไม่เหมือนกัน

A · CONTEXT ASSEMBLER (ตัวรวมบริบท)

สิ่งที่โมเดลจะได้มองเห็น

System prompt, ไฟล์ความจำ, ไฟล์โค้ดที่อ่าน, ระบบดึงข้อมูล (RAG), และการบีบอัดข้อมูลเมื่อบริบทล้น นี่คือตัวกำหนดคุณภาพของผลงานที่ใหญ่ที่สุด

B · DISPATCHER (ตัวแปลงคำสั่ง)

การอ่านโครงสร้างคำตอบ

แปลง JSON หรือ Tool Call Blocks ออกมาเป็นการกระทำจริง รองรับการแก้ไขปัญหาเมื่อโมเดลส่งพารามิเตอร์ผิดพลาด และจัดลำดับคิวการเรียกใช้งาน

C · TOOL RUNTIME (สภาพแวดล้อมรันเครื่องมือ)

จุดที่คำสั่งสัมผัสกับโลกจริง

ระบบตรวจสอบสิทธิ์ (Permissions), ระบบแยกสภาพแวดล้อมปลอดภัย (Sandboxing), กำหนดเวลาตัดจบ (Timeouts), และการเชื่อมต่อผ่านโพรโทคอล MCP

D · STATE MACHINE (ตัวจัดการสถานะ)

ประวัติและกิ่งก้านการทำงาน

บันทึกประวัติการคุยแบบแตกกิ่งได้ (Branchable), ความสามารถในการย้อนกลับ (Undo), และการบันทึกเซสชันลงดิสก์เพื่อกลับมาทำงานต่อได้

E · COMPACT / PRUNE (ระบบบีบอัดบริบท)

การป้องกันไม่ให้บริบทล้น

การตัดทอนผลลัพธ์ของคำสั่งเทอร์มินัลขนาดยาว, การสรุปใจความรอบที่ผ่านมา, และการรักษาโครงสร้างหน้าต่างข้อมูลไม่ให้ประสิทธิภาพลดลง

F · OBSERVABILITY (การสังเกตการณ์)

การมองเห็นสิ่งที่เกิดขึ้นจริง

การบันทึก Log การตัดสินใจ, การนับจำนวนโทเคน, การติดตามอัตรา Cache Hit, และการส่ง Telemetry ตรวจสอบข้อผิดพลาดของเครื่องมือ

 วิธีใช้งาน Harness ให้ได้ประสิทธิผลสูงสุด (How)

การใช้งาน Harness ให้ทรงพลัง สรุปเหลือเพียง 2 ทักษะหลัก

ทักษะที่ 1 (ABILITY ONE)

การควบคุม (Control)

คุณสามารถกำหนดสิ่งที่ส่งเข้าไปในโมเดลได้อย่างแม่นยำแค่ไหน — และหยุดมันได้ทันทีหรือไม่เมื่อเริ่มหลุดทาง?

บริบท (Context), คำสั่งหลัก (Instructions), สิทธิ์การเข้าถึง (Permissions), การเลือกโมเดล, และปุ่มหยุดฉุกเฉิน ทักษะการควบคุมคือสิ่งที่ทำให้งานสำเร็จได้ตั้งแต่ครั้งแรก แทนที่จะต้องแก้รอบที่สี่

ทักษะที่ 2 (ABILITY TWO)

การปล่อยลูปอัตโนมัติ (Loop)

คุณสามารถปล่อยให้เอเจนต์ทำงานต่อเนื่องโดยที่คุณไม่ต้องคอยนั่งเฝ้าหน้าจอได้ยาวนานแค่ไหน?

การตรวจสอบผลในตัว (Verification), การลองซ้ำเมื่อเครื่องมือพัง (Auto-retry), การย่อสรุปข้อมูล และการแยกโฟลเดอร์ทำงาน ทักษะลูปคือสิ่งที่ทำให้เอเจนต์ทำงานตอนคุณหลับได้อย่างปลอดภัย

สมการความสำเร็จ: ถ้าคุณมีแค่ Control คุณจะได้งานที่ดีแต่เหนื่อย เพราะต้องคอยพิมพ์สั่งทีละคำ... ถ้าคุณมีแค่ Loop คุณจะได้งานเร็วแต่งานอาจพัง เพราะปล่อยเอเจนต์วิ่งเตลิด... แต่เมื่อคุณมีทั้งสองอย่าง คุณจะกลายเป็นวิศวกรที่ทำงานได้เทียบเท่าคน 10 คน!

 ทักษะที่หนึ่ง: การควบคุม (Control)  ·  เรียงตามผลลัพธ์ที่ได้

5 คันโยกในการควบคุมอินพุตให้เฉียบคม

1

บริบท (Context) — กำหนดสิ่งที่อนุญาตให้เข้าสู่หน้าต่างข้อมูล

ไฟล์ความจำโปรเจกต์ (CLAUDE.md / AGENTS.md), การแนบไฟล์เจาะจง @file, การจำกัดโฟลเดอร์ทำงาน, และการเคลียร์ประวัติเก่าทิ้งเมื่อเริ่มงานใหม่ ปัญหาส่วนใหญ่ที่เอเจนต์ตอบแย่ มักเป็นเพราะปัญหาบริบทเน่า แต่ถูกเข้าใจผิดว่าเป็นเพราะเขียนพรอมต์ไม่ดี

2

System Prompt — กฎเหล็กที่ห้ามละเมิด

กำหนดบทบาท, วิธีการคิด, ข้อห้ามเด็ดขาด (เช่น "ห้ามลบโค้ดที่มีอยู่โดยไม่ถาม"), และมาตรฐานการเขียนโค้ดที่โมเดลต้องปฏิบัติตามเสมอ

3

หน้าต่างเครื่องมือ (Tool Surface) — ให้เฉพาะสิ่งที่จำเป็น

อย่าให้เครื่องมือมากเกินไป ยิ่งใส่เครื่องมือเยอะ โมเดลยิ่งสับสนและเสียโทเคนไปกับการอ่านสคีมาเครื่องมือ ให้เฉพาะเครื่องมือที่ต้องใช้กับงานนั้นจริงๆ

4

ระบบสิทธิ์ (Permissions) — ควบคุมด่านตรวจก่อนลงมือ

ตั้งค่าว่าการกระทำใดทำได้ทันที (Auto-approve) เช่น อ่านไฟล์ และการกระทำใดต้องรอมนุษย์กดยืนยัน (Approval-gated) เช่น ลบไฟล์, รัน Bash คำสั่งอันตราย

5

การสั่งหยุดกลางคัน (Interruptibility) — สั่งเบรกได้ทันใจ

ความสามารถในการกด Ctrl+C หรือ Escape เพื่อสั่งให้เอเจนต์หยุดคิดหรือหยุดรันเครื่องมือทันทีเมื่อเห็นว่าเริ่มผิดทาง โดยไม่ทำให้เซสชันหลุด

 ทักษะที่สอง: การปล่อยลูป (Loop)  ·  ทำอย่างไรให้ปล่อยเอเจนต์ทำงานได้ยาวนานขึ้น

5 คันโยกที่จะปลดล็อกให้เอเจนต์ทำงานต่อเนื่องได้อย่างปลอดภัย

คันโยกที่สำคัญที่สุด (THE ONE THAT MATTERS MOST)

การตรวจสอบผลลัพธ์ในลูป (Verification in the Loop)

ให้เครื่องมือที่เอเจนต์สามารถใช้ตรวจให้คะแนนตัวเองได้ — เช่น การรันชุดทดสอบ (Tests), Typecheck, Linter, สั่ง Build โปรเจกต์ หรือแม้แต่ส่งโค้ดให้เอเจนต์ตัวที่สองช่วยรีวิว เมื่อมีสิ่งนี้ ลูปจะไม่ใช่การเสี่ยงดวงอีกต่อไป หากไม่มีสิ่งนี้ การปล่อยเอเจนต์วิ่งยาวขึ้นก็มีแต่จะได้โค้ดพังๆ ที่ไม่ได้ตรวจทานเพิ่มขึ้นเป็นกองพะเนิน

"การแยกเอเจนต์ที่ลงมือทำงาน ออกจากเอเจนต์ที่คอยตรวจความถูกต้อง คือเคล็ดลับสำคัญที่ทำให้ได้ผลลัพธ์ระดับโปรดักชัน"

2 · การลองใหม่อัตโนมัติ (AUTO-RETRY)

การกู้คืนเมื่อเครื่องมือเกิด Error

เมื่อรัน Bash แล้วพัง หรือโมเดลเรียกไฟล์ที่ไม่มีอยู่ Harness ที่ดีจะไม่หยุดทำงานหรือโยนข้อผิดพลาดใส่มนุษย์ทันที แต่มันจะส่ง Error Message กลับไปให้โมเดลอ่านในรอบถัดไป เพื่อให้โมเดลคิดหาวิธีแก้ปัญหาด้วยตัวเอง

3 · กลยุทธ์การบีบอัด (COMPACTION)

การตัดทอนประวัติเก่าอย่างชาญฉลาด

เมื่อบริบทเริ่มเต็ม ให้สรุปใจความสิ่งที่ทำสำเร็จแล้ว และคงไว้เฉพาะไฟล์สำคัญ ป้องกันไม่ให้เสียค่าใช้จ่ายซ้ำซ้อนและป้องกันไม่ให้โมเดลสับสน

4 · การแยกสภาพแวดล้อม (WORKTREE ISOLATION)

หนึ่งเอเจนต์ หนึ่งโฟลเดอร์ทำงาน

ใช้ Git Worktrees แยกโฟลเดอร์ให้แต่ละเอเจนต์อย่างเด็ดขาด เอเจนต์จะไม่แย่งกันแก้ไขไฟล์เดิม และถ้าเอเจนต์ตัวไหนทำพัง เราแค่ลบโฟลเดอร์นั้นทิ้งได้โดยไม่กระทบโค้ดหลัก

5 · ความยาวของสายจูง (LEASH LENGTH)

กำหนดจำนวนรอบสูงสุด (Max Turns)

ตั้งเพดานความยาว เช่น ไม่เกิน 30-50 รอบ เพื่อป้องกันไม่ให้เอเจนต์วนลูปไม่รู้จบจนเงินในกระเป๋าของคุณหมดเกลี้ยง

 การวัดผลและการสังเกตการณ์ (Instrumentation)

ตัวเลขเพียง 2 ตัวที่สามารถทำนายแทบทุกสิ่งทุกอย่างในระบบ

ตัวชี้วัดที่ 1 · คุณภาพ (QUALITY)

ณ วินาทีนี้ มีอะไรอยู่ในบริบท (Context) ของคุณจริงๆ บ้าง?

ไม่ใช่สิ่งที่คุณ คิด ว่าคุณส่งไป... แต่เป็นสิ่งที่ตัว Harness ทำการประกอบรวมร่างขึ้นมาส่งให้โมเดลจริงๆ: System prompt, นิยามเครื่องมือ, ไฟล์คู่มือ, ทุกไฟล์ที่เอเจนต์เคยแอบเปิดอ่านในเซสชันนี้, และประวัติบทสนทนาทั้งหมด

  • บน Claude Code: พิมพ์คำสั่ง /context เพื่อตรวจเช็ค
  • บน Harness อื่นๆ: ให้ดัมป์ก้อน Request ออกมาดูว่ามีอะไรแอบยัดเข้าไปบ้าง
  • ถ้าโมเดลเริ่มตอบหลอนหรือทำงานแย่ลง ให้ตรวจตัวชี้วัดนี้เป็นอันดับแรก 90% ของปัญหาคือมีขยะล้นอยู่ในบริบท!
ตัวชี้วัดที่ 2 · ต้นทุน (COST)

ต้นทุนเฉลี่ยต่อหนึ่งรอบการทำงาน (Cost per Turn)

อัตราส่วนว่าคุณใช้ประโยชน์จาก Prompt Caching ได้คุ้มค่าแค่ไหน เพราะการอ่านแคชถูกกว่าการส่งใหม่เต็มๆ ถึง 90%!

  • รอบที่ 1: จ่ายเต็มราคา + ค่าเขียนแคช (Cache Write 1.25×)
  • รอบที่ 2 ถึง 40: ถ้าไม่มีอะไรไปกวนหัวแคช จะจ่ายแค่ค่าดึงแคช (Cache Read 0.1× เท่านั้น!)
  • ถ้าต้นทุนเฉลี่ยต่อรอบของคุณสูงผิดปกติ แปลว่ามีบั๊กบางอย่างใน Harness ที่ทำให้แคชหลุดทุกรอบ
สูตรจำสำหรับวิศวกร: อย่าดูแค่บิลค่าใช้จ่ายรวมตอนสิ้นเดือน ให้ดู Context Composition (สิ่งที่อยู่ในหน้าต่าง) และ Cache Hit Rate (เปอร์เซ็นต์การดึงแคชสำเร็จ) สองตัวนี้จะบอกคุณทุกอย่างว่าระบบกำลังมีสุขภาพดีหรือกำลังเน่าเปื่อย

 กลไกแคช (How)  ·  คลิกที่แต่ละบล็อกเพื่อจำลองการแก้ไขข้อมูลและดูว่าแคชพังอย่างไร

Terminal Multiplexer คือโปรแกรมที่ทำหน้าที่ แยกโปรเซสการทำงาน ออกจากหน้าต่างจอภาพ (Decouples process from window)

หนึ่งหน้าจอเทอร์มินัล สามารถเปิดได้หลายเซสชันอิสระพร้อมกัน คุณสั่ง Detach (ถอดหน้าจอออก) โปรเซสก็ยังคงรันต่อไม่หยุด สัญญาณเน็ตหลุดหรือ SSH ตัด เซิร์ฟเวอร์ก็ไม่ตาย กลับมาเปิดใหม่เมื่อไหร่ ทุกอย่างก็ยังอยู่ที่เดิมเป๊ะ

ในอดีต มันมีประโยชน์สำหรับงานคอมไพล์โค้ดยาวๆ บนเซิร์ฟเวอร์... แต่สำหรับ AI Agent ยุคนี้ มันกลายเป็น โครงสร้างพื้นฐานที่ขาดไม่ได้ (Structural necessity)

ทำไมเอเจนต์ถึงเปลี่ยนความต้องการนี้: เอเจนต์ทำงานต่อเนื่องยาวนานหลายสิบนาที และต้องการรอการอนุมัติจากมนุษย์เป็นช่วงๆ ถ้าไม่มี Multiplexer หน้าจอของคุณจะถูกยึด และคุณจะไม่สามารถสั่งงานเอเจนต์ตัวที่สองได้เลย

นี่คือสะพานเชื่อมระหว่างสองซีกของการบรรยายนี้: ถ้าตัว Multiplexer มี Socket API ให้เรียกใช้งานได้ นั่นหมายความว่า "คำสั่งเปิดหน้าต่างใหม่ (Spawn a pane)" ก็จะกลายเป็นเพียง Tool Call ธรรมดาตัวหนึ่ง ที่ตัว Harness สามารถสั่งงานได้เอง!

กลไกของ HARNESS ขนาดจิ๋วตัวนี้:
  • รับรายการงานทั้งหมดที่ต้องทำ (Task List)
  • เปิดหน้าต่างแยกให้แต่ละงาน โดยมีเอเจนต์ตัวจริงนั่งรันอยู่ข้างใน
  • ตรวจสอบสถานะการทำงานผ่าน Unix Socket
  • ส่งเสียงเตือนเรียกคุณเฉพาะตอนที่มีหน้าต่างติด Blocked รอการตัดสินใจ
  • ปิดหน้าต่างและเก็บกวาดให้เรียบร้อยเมื่องานสำเร็จสมบูรณ์

    sock = socket.socket(socket.AF_UNIX)

    }
    sock.send(json.dumps(payload))

3 อาการของ CONTEXT ROT
  • ลืมกฎหลัก: โมเดลเริ่มละเมิดข้อห้ามใน System Prompt เช่น แอบลบโค้ดที่มีอยู่

  • ความฉลาดถดถอย: โมเดลระดับเรือธงเริ่มตอบคำถามผิดในระดับเด็กประถม
บทเรียนสำหรับมือใหม่: อย่าหลงเชื่อตัวเลขสเปก 1M หรือ 2M Context Window ว่ายัดอะไรลงไปก็ได้ เพราะยิ่งยัดเยอะ ผลงานยิ่งแย่และค่าใช้จ่ายยิ่งพุ่ง!

        # ขั้นที่ 1 & 2: รวมบริบทแล้วยิงเรียกโมเดล
        resp = client.messages.create(
            model="claude-3-7-sonnet-latest",
            max_tokens=4096,
            system=SYSTEM,
            tools=TOOLS,
            messages=msgs
        )
        # ขั้นที่ 3: ต่อข้อความของโมเดลเข้าประวัติ
        msgs.append({"role": "assistant", "content": resp.content})
        
        # ตรวจดูว่ามีคำสั่งเรียก Tool ไหม? ถ้าไม่มี แปลว่าเสร็จสิ้น!
        tool_calls = [b for b in resp.content if b.type == "tool_use"]
        if not tool_calls:
            return resp.content  # จบการทำงาน ส่งคำตอบสุดท้าย
            
        # ขั้นที่ 4 & 5: สั่งรันเครื่องมือ แล้วเอาผลลัพธ์ใส่กลับเข้าไป
        results = []
        for t in tool_calls:
            out = execute_tool(t.name, t.input) # รันคำสั่งจริงในเครื่อง
            results.append({
                "type": "tool_result",
                "tool_use_id": t.id,
                "content": str(out)
            })
        msgs.append({"role": "user", "content": results})
    raise RuntimeError("ติดเพดานจำนวนรอบสูงสุด (Max turns exceeded)")
แก่นแท้ 5 ขั้นตอนตรงตามทฤษฎีเป๊ะ

สังเกตในโค้ด: 1) รวมข้อความ msgs, 2) ยิงเรียก API, 3) ต่อคำตอบเข้าประวัติ, 4) ถ้ามี tool_use ให้รันฟังก์ชัน, 5) เอาผลลัพธ์ใส่เป็นบทบาท user แล้ววนลูปกลับไปทำข้อ 1 ใหม่!

ความลับของทั้งวงการ: ทุกโปรแกรมเอเจนต์มูลค่าพันล้านดอลลาร์ในตลาด ข้างในมีโครงสร้างแก่นลูปเหมือนโค้ด 40 บรรทัดนี้ทั้งสิ้น!

 ความจริงของวิศวกรรม (Build your own · the honest part)

ทุกสิ่งที่อยู่หลังบรรทัดที่ 40 ต่างหากคือ "ตัวผลิตภัณฑ์จริง"

การเขียนลูป 40 บรรทัดใช้เวลาแค่สุดสัปดาห์เดียว... แต่รายการต่อไปนี้คือสิ่งที่วิศวกรต้องใช้เวลาพัฒนาเป็นแรมปี และนี่คือสนามแข่งขันที่แท้จริง:

กลยุทธ์บริบท (Context Strategy)

จะเลือกไฟล์ไหนเข้าไป จะค้นคืนข้อมูลอย่างไร เมื่อไหร่ควรบีบอัดประวัติ และไฟล์ไหนห้ามส่งซ้ำ นี่คือส่วนที่ยากและมีมูลค่าสูงที่สุด

วินัยเรื่องแคช (Cache Discipline)

การเรียงลำดับบล็อกให้คงที่, การจัดเรียงสคีมาเครื่องมือแบบ Deterministic, และการห้ามใส่ Timestamp ที่หัวขบวน เพื่อให้แคชไม่หลุด

ความปลอดภัย (Safety & Sandbox)

การแยกสภาพแวดล้อมรันโค้ด, ป้องกันไม่ให้โมเดลรันคำสั่ง rm -rf /, การควบคุมสิทธิ์การเขียนไฟล์ และป้องกัน Prompt Injection

การกู้คืนข้อผิดพลาด (Error Recovery)

เมื่อเครื่องมือส่งผลลัพธ์ Error หรือส่ง JSON พัง จะทำอย่างไรให้เอเจนต์ไม่หยุดทำงานแต่สามารถแก้ไขตัวเองได้

อินเทอร์เฟซผู้ใช้ (User Experience)

การสตรีมตัวอักษรแบบสดๆ, การแสดงผลตาราง Diff เปรียบเทียบโค้ดก่อน-หลังแก้, การมีปุ่มลัดกดยกเลิกฉุกเฉิน

การตรวจสอบผล (Verification Loop)

การฝังระบบรันเทสต์, การเชื่อมต่อ Language Server (LSP) เพื่อเช็คไวยากรณ์ และการใช้เอเจนต์ตัวที่สองตรวจโค้ด

6 บทเรียนสำคัญที่คุณต้องจดจำและนำไปใช้

1 · Harness คือผลงานของคุณครึ่งหนึ่ง

ตัวเลขวัดผลพิสูจน์แล้วว่าโมเดลเดิมแต่ต่าง Harness คะแนนต่างกันถึง 34 แต้ม ต่อไปนี้อย่าพูดถึงคะแนนโมเดลโดยไม่ถามว่ารันบน Harness ตัวไหนอีก

2 · แยกให้ออกว่าคุณกำลังพูดถึงเลเยอร์ไหน

Harness คุมลูป (Loop), Multiplexer คุมโปรเซส (Process), OS คุมการแยกความปลอดภัย (Isolation) ความสับสนส่วนใหญ่ในวงการเกิดจากการคุยสลับเลเยอร์กัน

3 · Control และ Loop คือสองทักษะคนละด้าน

คุมอินพุตให้กระชับแม่นยำด้วยการจัดบริบท และขยายความยาวการปล่อยลูปด้วยการฝังระบบตรวจทานผลลัพธ์ (Verification in the Loop)

4 · แคชคือ Prefix และมันเปราะบางมาก

เงินในกระเป๋าของคุณขึ้นอยู่กับว่าบล็อกหัวขบวนไม่ถูกรบกวน จัดระเบียบบริบทให้คงที่ แล้วคุณจะประหยัดค่าใช้จ่ายได้ถึง 80-90%

5 · คอขวดของงานได้ย้ายมาอยู่ที่ตัวคุณเองแล้ว

เมื่อคุณมีเอเจนต์ 6 ตัวทำงานพร้อมกัน ทรัพยากรที่มีค่าที่สุดคือความสนใจของคุณ จงใช้ Multiplexer ที่ฉลาดและดูเฉพาะตัวที่ติด Blocked เท่านั้น

6 · บริบทคือหนี้สิน ไม่ใช่สินทรัพย์

อย่าภูมิใจกับการยัดข้อมูล 200k โทเคนลงในหน้าต่าง เพราะโมเดลจะเริ่มเอ๋อ ยิ่งบริบทสั้นและตรงจุดเท่าไหร่ งานยิ่งออกมาสมบูรณ์แบบเท่านั้น
