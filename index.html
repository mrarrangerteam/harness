เจาะลึกกลไก AI Coding Agent จากศูนย์ (Pi from Scratch)

ถอดรหัสเบื้องหลัง AI ช่วยเขียนโค้ด (เช่น Claude Code, Cursor, Pi, Devin) ผ่านโปรเจกต์มินิมอล nanopi ที่ประกอบด้วย 5 ไฟล์ TypeScript เล็กๆ เท่านั้น เข้าใจง่ายด้วยภาพเปรียบเทียบ อุปมาเชิงสถาปัตยกรรม และตัวอย่างโค้ดจริง

“What I cannot create, I do not understand.” — Richard Feynman
(สิ่งใดที่ฉันสร้างขึ้นมาเองไม่ได้ แปลว่าฉันยังไม่เข้าใจมันอย่างแท้จริง)

🗺️ บทที่ 1: The Map (แผนผังระบบ 5 โมดูล)

ลองจินตนาการว่า nanopi คือ "เวิร์กช็อปขนาดย่อม" (Tiny Workshop) ในโรงงาน โดยแต่ละไฟล์มีหน้าที่ชัดเจน ไม่ก้าวก่ายกัน:

🗣️ llm.ts (ล่ามประจำประตู)
คอยคุยกับสมอง AI แปลงภาษา API ส่งเข้าส่งออก
👷 agent.ts (โฟร์แมนคุมหน้างาน)
คอยวางแผน วนลูปถาม AI แล้วสั่งช่างหยิบเครื่องมือ
🧰 tools.ts (กล่องเครื่องมือช่าง)
เครื่องมือแตะไฟล์และรันคำสั่ง bash บนเครื่องจริง
🛎️ tui.ts (โต๊ะประชาสัมพันธ์)
รับคำสั่งจากผู้ใช้ และพิมพ์ข้อความทีละตัวอักษร
🔌 cli.ts (รางปลั๊กพ่วงรวมสายไฟ)
จุดเชื่อมต่อทุกชิ้นส่วนเข้าด้วยกัน และบันทึกประวัติลง session.jsonl

📌 3 คำศัพท์พื้นฐานที่ต้องรู้ก่อนเริ่ม:

  • 1. LLM (Large Language Model): สมองกลที่สร้างข้อความ และสามารถ "ขอใช้เครื่องมือที่กำหนดได้" (Tool Call) แต่ตัว LLM เอง ไม่สามารถ แตะไฟล์หรือรันคำสั่งในคอมพิวเตอร์ของคุณได้โดยตรง
  • 2. Context (สมุดโน้ตประจำงาน): ข้อมูล JSON ที่เก็บ System Prompt, ประวัติการสนทนา, คำสั่งเรียกเครื่องมือ และผลลัพธ์ที่ได้จากการรันเครื่องมือ นี่คือ "ความทรงจำเดียว" ของ Agent
  • 3. Event (ใบแจ้งสถานะย่อย): ข้อความแจ้งความคืบหน้าที่ถูกส่งออกมาระหว่างที่งานกำลังทำอยู่ (Real-time stream) เช่น กำลังพิมพ์ข้อความ หรือกำลังสั่งรัน Tool โดยไม่ต้องรอให้จบลูปทั้งก้อน

Diagram: The 5-Module Map

งานเริ่มต้นจาก Command Line เข้าสู่ระบบ Agent คอยประสานงานระหว่าง Model กับ Tools และส่งผลลัพธ์กลับสู่ Terminal

(3. โฟร์แมนคุมลูปการทำงาน)"] A --> L["🗣️ llm.ts talks to the model
(4. ล่ามแปลภาษาคุยกับ AI)"] A --> T["🧰 tools.ts acts on the computer
(5. กล่องเครื่องมือแก้ไฟล์/รันคำสั่ง)"] C --> V["🖥️ tui.ts shows progress
(6. หน้าจอพิมพ์ผลลัพธ์แบบเรียลไทม์)"]

1. llm.ts — ล่ามประจำประตูโรงงาน (The Translator)

src/llm.ts

llm.ts ทำหน้าที่เหมือน "ล่ามแปลภาษา" โมเดลแต่ละค่าย (OpenAI, Anthropic, Ollama, GLM) มีรูปแบบข้อมูลส่งผ่านสาย (Wire-format) ที่ไม่เหมือนกัน โค้ดส่วนอื่นของโปรแกรมไม่ควรต้องมารับรู้เรื่องนี้

flowchart TB C["Context
(สมุดโน้ตบันทึกประวัติ)"] --> M["Convert it to API messages
(แปลงเป็นรูปแบบข้อความที่ API เข้าใจ)"] M --> A["Call an OpenAI-compatible API
(ยิง Request ไปยังเซิร์ฟเวอร์ AI)"] A --> S["Read small SSE chunks
(ทยอยอ่านชิ้นส่วนคำตอบที่ไหลกลับมา)"] S --> E["Emit StreamEvent values
(ส่งต่อเหตุการณ์สถานะให้ระบบ)"]

ฟังก์ชันหลักคือ stream() จะส่ง Context ปัจจุบันไปยัง Endpoint /chat/completions แบบ OpenAI-compatible ข้อมูลจะไหลกลับมาผ่าน SSE (Server-Sent Events) ซึ่ง llm.ts จะแกะเป็น 4 เหตุการณ์มาตรฐาน:

text_delta: ตัวอักษรชุดถัดไปที่โมเดลพิมพ์
tool_call: คำขอสั่งรัน Tool ที่ประกอบร่างเสร็จสมบูรณ์แล้ว
done: การสตรีมสิ้นสุดลง พร้อมเหตุผล (เช่น สั่งจบ หรือถูกตัด)
error: เกิดข้อผิดพลาดในระดับ Request หรือ Stream
💡 เคล็ดลับสถาปัตยกรรม: พารามิเตอร์ของ Tool มักถูกสตรีมมาเป็นชิ้นส่วนเล็กๆ (JSON Chunks) หน้าที่ของ llm.ts คือต้องสะสม (Buffer) ชิ้นส่วนเหล่านั้นจนครบก้อน แล้วจึงปล่อย tool_call ที่สมบูรณ์ออกมาให้ Agent เพื่อป้องกัน Agent ได้รับ JSON แหว่ง!

2. agent.ts — โฟร์แมนคุมหน้างาน (The Foreman)

src/agent.ts

หัวใจของ Agent ทั้งหมดคือ while loop ธรรมดาๆ ที่ทรงพลัง:

flowchart TB C["Context
(เปิดอ่านสมุดโน้ตประวัติล่าสุด)"] --> M["Ask LLM
(ส่งถามสมอง AI ว่าต้องทำอะไร)"] M --> D{"Was tool requested?
(AI ขอให้รันเครื่องมือหรือไม่?)"} D -- "ใช่ (Yes)" --> T["Run tools in order
(สั่งรันเครื่องมือช่างตามลำดับ)"] T --> R["Add results to context
(จดผลการรันกลับลงสมุดโน้ต)"] R --> M D -- "ไม่ (No)" --> E["End turn
(จบงาน พิมพ์คำตอบสมบูรณ์ให้ผู้ใช้)"]
  1. อ่าน Context ปัจจุบันแล้วถาม LLM ว่าควรทำอย่างไรต่อไป
  2. ถ้า LLM ขอให้รัน Tool → หยิบเครื่องมือใน tools.ts มารันตามลำดับ
  3. นำข้อความตอบกลับของ Assistant และผลการรัน Tool (Tool Result) บันทึกลงใน Context
  4. วนลูปกลับไปถาม LLM ใหม่อีกครั้ง จนกว่า LLM จะหยุดขอใช้ Tool
💡 ข้อสังเกตสำคัญ: runAgent() จะแก้ไข Context ที่ส่งเข้ามาแบบ in-place (เปลี่ยนแปลงในตัวแปรเดิม) ตัว Agent ไม่มีที่เก็บประวัติความลับแยกไว้ข้างในเลย ประวัติทั้งหมดอยู่ในสมุดโน้ตเล่มนี้เท่านั้น!

3. tools.ts — กล่องเครื่องมือช่าง (The Toolbox)

src/tools.ts

tools.ts รวบรวม 4 เครื่องมือทรงพลัง (Built-in Tools):

📖 read_file
อ่านไฟล์ข้อความ (หากยาวเกิน 200 บรรทัด จะตัดหาง 200 บรรทัดล่าสุด แล้วเซฟไฟล์เต็มไว้ใน temp)
✍️ write_file
สร้างโฟลเดอร์ให้อัตโนมัติ (mkdir recursive) และเขียนทับไฟล์เป้าหมายแบบสมบูรณ์
✂️ edit
ค้นหาและแทนที่ข้อความที่ตรงกัน แบบมีแค่จุดเดียวเท่านั้น (Uniquely match) ป้องกันการแก้ผิดจุด
⚡ run_bash
รันคำสั่ง Terminal Shell จริง มี Timeout 30 วินาที และรองรับ AbortSignal ดักยกเลิก
⚠️ เครื่องมือเหล่านี้ไม่ใช่ Pure Functions: เครื่องมือเหล่านี้มี Side Effects โดยตรงต่อระบบไฟล์และกระบวนการทำงานในเครื่องของคุณ! จึงต้องระมัดระวังเหมือนเครื่องมือช่างไฟฟ้าของจริง

4. tui.ts — โต๊ะประชาสัมพันธ์ (Front Desk)

ดูแลหน้าจอ Terminal ด้วยโมดูล readline ของ Node.js คอยรับคำสั่ง พิมพ์ผลลัพธ์แบบเรียลไทม์ และมีระบบ Busy State:

  • เมื่อกำลังประมวลผลอยู่ จะล็อกไม่ให้ผู้ใช้พิมพ์แทรกจนกว่าจะเสร็จ
  • ถ้ากด Ctrl+C ตอนกำลัง Busy จะส่งสัญญาณยกเลิก (Abort) ไปยัง Agent
  • tui.ts ไม่รู้จัก LLM หรือ Tools เลย รู้จักแค่การแสดงผลข้อความ

5. cli.ts — รางปลั๊กพ่วง (Power Strip)

ทำหน้าที่เป็น Composition Root หรือจุดเดียวที่เสียบปลั๊กทุกชิ้นส่วนเข้าหากัน:

  • อ่าน Environment Variables: NANOPI_API_KEY, NANOPI_MODEL
  • โหลดประวัติเก่าจาก ~/.nanopi/session.jsonl
  • สร้าง AbortController ใหม่ทุกครั้งที่ผู้ใช้ส่งคำสั่ง
  • เมื่อจบเทิร์น บันทึกข้อความใหม่ต่อท้ายไฟล์ (Append-only)
💡 ตัวอย่างสถานการณ์จำลองจริงทีละวินาที (Step-by-Step Scenario Walkthrough)

สมมุติผู้ใช้พิมพ์สั่งว่า: "ช่วยแก้คำว่า bug เป็น fix ในไฟล์ index.html ให้หน่อย"

นี่คือสิ่งที่เกิดขึ้นจริงภายใน 5 ไฟล์ในเวลาเพียง 5 วินาที:

1
🛎️ tui.ts: รับข้อความที่คุณพิมพ์เข้ามา แล้วปรับสถานะเป็น busy = true (ล็อกไม่ให้พิมพ์ข้อความใหม่แทรก)
2
🔌 cli.ts: นำข้อความใส่ลงในสมุดโน้ต Context แล้วเรียก runAgent() ใน agent.ts
3
👷 agent.ts & 🗣️ llm.ts: ส่งสมุดโน้ตไปถามสมอง AI โมเดลตอบกลับมาว่า "ขอใช้เครื่องมือ read_file('index.html') เพื่อดูโค้ดก่อน"
4
🧰 tools.ts: อ่านไฟล์ index.html บนฮาร์ดดิสก์จริง ได้เนื้อหาไฟล์กลับมา แล้วส่งให้ agent.ts จดบันทึกผลลัพธ์ลงสมุดโน้ต
5
👷 agent.ts (วนลูปถามซ้ำ): ส่งเนื้อหาไฟล์กลับไปถาม AI อีกรอบ AI วิเคราะห์แล้วสั่ง "เจอจุดแล้ว ขอใช้เครื่องมือ edit(path, old_string='bug', new_string='fix')"
6
🧰 tools.ts: ค้นหาคำว่า bug จุดเดียวแล้วแก้เป็น fix ทันที แล้วตอบกลับมาว่า "แก้ไขเสร็จแล้ว 1 จุด"
7
🛎️ tui.ts: AI พิมพ์ตอบคุณว่า "ผมได้แก้ไขคำว่า bug เป็น fix ให้เรียบร้อยแล้วครับ!" แล้วปลดล็อกสถานะ busy = false พร้อมรับคำสั่งถัดไปของคุณ!

🔄 วงจรการทำงาน 1 รอบเต็ม (One Complete Turn)

flowchart TB I["1. tui.ts รับคำสั่ง
(Readline รับข้อความผู้ใช้)"] --> C["2. cli.ts จดลง Context
(บันทึกเป็นข้อความใหม่ในสมุดโน้ต)"] C --> A["3. agent.ts เริ่มลูป
(สั่งเปิด while loop คุมงาน)"] A --> L["4. llm.ts สตรีมข้อมูล
(ส่งถาม AI และรับ SSE Stream)"] L --> D{"Is there tool call?
(AI สั่งเรียกใช้เครื่องมือหรือไม่?)"} D -- "มี (Yes)" --> T["5. tools.ts ทำงานจริง
(อ่าน/เขียนไฟล์ หรือรันคำสั่ง bash)"] T --> A D -- "ไม่มี (No)" --> I

สรุปหลักคิดทางสถาปัตยกรรม: Context คือสมุดโน้ต (The Notebook), Events คือใบแจ้งสถานะ (Status Slips) และ CLI คือสายไฟเชื่อมโยง (The Wiring) การแยกบทบาทแบบนี้ทำให้เราสามารถเปลี่ยนหน้าจอ (เช่น ย้ายจาก Terminal ไปเป็น Web UI) หรือเปลี่ยนผู้ให้บริการ LLM ได้ทันทีโดยไม่ต้องแก้ Work Loop ส่วนกลางเลยแม้แต่บรรทัดเดียว!

สรุป 5 ไฟล์หลัก (ฉบับมือใหม่เข้าใจทันที)

เปรียบเทียบชัดเจน
🗣️ src/llm.ts (ล่ามแปลภาษา) ~338 บรรทัด
หน้าที่: คุยกับสมอง AI ผ่านสายโทรศัพท์อินเทอร์เน็ต
• SSE Stream: เหมือน "ก๊อกน้ำเปิดไหลทีละหยด" ตัวหนังสือพิมพ์วิ่งออกมาทีละคำ
• text_delta: เศษคำแต่ละหยด เช่น "ส", "วัส", "ดี"
• tool_call: AI บอกว่า "ช่วยหยิบเครื่องมืออ่านไฟล์ให้หน่อย"
👷 src/agent.ts (โฟร์แมนคุมงาน) ~218 บรรทัด
หน้าที่: ไม่ลงมือแก้ไฟล์เอง แต่คอยสั่งการและจดบันทึก
• while loop: ลูปทำงานซ้ำ "ถาม AI -> สั่งช่างทำ -> เอาผลกลับไปถาม AI" จนเสร็จ
• max_tokens: ป้องกันกรณี "หมึกหมดกลางคัน" ถ้าคำสั่งขาดห้ามนำไปรัน
• Abort: ปุ่ม "หยุดฉุกเฉิน" เมื่องานถูกยกเลิก (Ctrl+C) ให้หยุดอย่างปลอดภัย
🧰 src/tools.ts (กล่องเครื่องมือช่าง) ~154 บรรทัด
หน้าที่: ค้อน เลื่อย ไขควง ที่ลงมือแตะต้องไฟล์และคอมพิวเตอร์จริง
• 4 เครื่องมือ: read_file (อ่าน), write_file (เขียน), edit (แก้เฉพาะจุด), run_bash (รันคำสั่ง)
• Truncate 200: ถ้าไฟล์ยาวเป็นหมื่นบรรทัด จะตัดส่งแค่ 200 บรรทัดท้าย ป้องกันสมุดโน้ตล้น
🛎️ src/tui.ts (โต๊ะประชาสัมพันธ์) ~91 บรรทัด
หน้าที่: คอยคุยกับผู้ใช้ที่หน้าจอ Terminal
• Readline: รอรับข้อความที่คุณพิมพ์แล้วกด Enter
• Busy State: ขึ้นป้าย "กำลังทำงาน ห้ามกวน" กันผู้ใช้พิมพ์แทรกตอน AI คิด
🔌 src/cli.ts (รางปลั๊กพ่วงรวมสาย) ~128 บรรทัด
หน้าที่: เอาสายไฟของทั้ง 4 โมดูลมาเสียบปลั๊กรวมกันให้ทำงานได้
• Composition Root: สวิตช์เมนบอร์ดที่เปิดแล้วทั้งระบบทำงานพร้อมกัน
• Session JSONL: สมุดบันทึกประวัติเซฟลงไฟล์ 1 บรรทัด = 1 ข้อความ เปิดใหม่ก็คุยต่อได้

🛠️ บทที่ 2: สร้าง nano-pi ทีละขั้นตอน (23 สเต็ปอย่างละเอียด)

ติดตามเส้นทางของข้อมูล (Follow the Data) ในการประกอบ Coding Agent ทีละชิ้นส่วน จากลูปจำลอง จนถึงระบบ Session ที่บันทึกประวัติการสนทนาลงฮาร์ดดิสก์

ช่วงที่ 1: แกนกลางและโครงสร้างข้อมูล (Steps 1 - 3)

กำหนดโมเดลทางความคิด (Mental Model) และนิยาม Type สำหรับการสนทนา

Step 01 src/agent.ts

1. Start with the loop (เริ่มจากโครงลูป)

เริ่มต้นด้วย while (true) ใน runAgent() ซึ่งเป็น async generator ที่ส่งผลลัพธ์ผ่าน yield ลูปนี้ไม่มีการล็อกจำนวนรอบตายตัว (No hard-coded step limit) จะหยุดก็ต่อเมื่อโมเดลตอบเสร็จ, ผู้ใช้กดยกเลิก, หรือระบบพัง

Step 02 src/llm.ts

2. Define the translator's data (นิยามประเภทข้อมูลของล่าม)

กำหนด TypeScript Types สำหรับ Model (apiKey, model, baseUrl, maxTokens) และ Context ซึ่งประกอบด้วย systemPrompt? และอาร์เรย์ messages: Message[] ทั้งหมดเป็น Plain JSON ไม่มีฟังก์ชันซ่อนอยู่ เพื่อให้บันทึกและโหลดกลับมาได้ง่าย

Step 03 src/llm.ts

3. Receive the reply as a stream (รับคำตอบแบบสตรีมมิ่ง)

ฟังก์ชัน stream() ประกาศเป็น async function* ส่งคืน AsyncGenerator<StreamEvent> โดยมี 4 เหตุการณ์: text_delta, tool_call, done, และ error ทำให้หน้าจอแสดงตัวอักษรวิ่งได้ทันทีโดยไม่ต้องรอให้โมเดลคิดจนจบ

ช่วงที่ 2: การสื่อสารทางเครือข่ายและการแปลงโปรโตคอล (Steps 4 - 8)

รับส่ง HTTP POST, ถอดรหัส SSE Chunks, และแปลงข้อความเข้าออกระหว่าง Format ภายในกับ OpenAI API

Step 04 src/llm.ts

4. Send the request (ส่ง Request ไปยัง API)

ยิง HTTP POST ไปที่ /chat/completions โดยแนบ stream: true, API Key ใน Header Authorization: Bearer ... และส่ง AbortSignal เข้าไปด้วยเพื่อเปิดโอกาสให้หยุดคำขอระหว่างทางได้

Step 05 src/llm.ts

5. Translate one update (ถอดรหัสบรรทัด SSE ทีละบรรทัด)

handleSSELine() ตัดคำว่า data: ออกแล้ว Parse JSON ถ้าเป็นข้อความธรรมดาจะส่งออกทันที แต่ถ้าเป็น Tool Call arguments ที่ทยอยมาเป็นชิ้นๆ จะนำไปเก็บพักใน Buffer ตาม Index ก่อน

Step 06 src/llm.ts

6. Read every update (อ่าน Stream จนจบบอดี้)

ใช้ TextDecoder แปลงไบต์เป็นข้อความ และมีตัวแปร buf คอยต่อข้อความที่ค้างอยู่ เมื่อ Stream จบสมบูรณ์ จึงทำการ flushToolCalls() เรียงตามลำดับ Index แล้วปล่อย Event done

Step 07 src/llm.ts

7. Convert notebook entries (แปลงสมุดโน้ตเป็น Message ของ OpenAI)

contextToOpenAIMessages() แปลงรูปแบบภายในของ nanopi ให้อยู่ในฟอร์แมตที่ OpenAI คาดหวัง: แยก System Prompt เป็น role system, รวมบล็อกคำสั่งเครื่องมือเป็น tool_calls, และเปลี่ยนผลลัพธ์เครื่องมือเป็น role tool

Step 08 src/llm.ts

8. Add replies to the notebook (นำคำตอบโมเดลจดกลับลงสมุดโน้ต)

ฟังก์ชัน buildAssistantMessage() และ buildToolResultMessage() ทำหน้าที่จัดระเบียบข้อความตอบกลับของ Assistant และผลลัพธ์ Tool Result ทั้งหมดให้พร้อมต่อท้ายอาร์เรย์ context.messages

ช่วงที่ 3: กล่องเครื่องมือช่าง (Steps 9 - 14)

การสร้าง Interface มาตรฐานของเครื่องมือ และเขียน 4 ฟังก์ชันอ่าน เขียน แก้ไฟล์ และรัน Terminal

Step 09 src/agent.ts

9. Give every tool one shape (กำหนดสัญญามาตรฐานให้ทุกเครื่องมือ)

อินเตอร์เฟส AgentTool กำหนดว่าเครื่องมือทุกชิ้นต้องมี: name, description, parameters (อธิบายฟิลด์ด้วย JSON Schema), และฟังก์ชัน execute(args, signal) ที่คืนค่าเป็น Promise<string>

Step 10 src/tools.ts

10. Open the toolbox (เปิดกล่องเครื่องมือ)

เริ่มต้นไฟล์ tools.ts เครื่องมือในนี้ไม่มีสิทธิ์เข้าถึงหรือแก้ไขสมุดโน้ต (Context) โดยตรง มันรับแค่ Parameter และคืนค่าเป็นข้อความธรรมดา เพื่อแยกตรรกะการรันเครื่องมือออกจากสเตตของ Agent

Step 11 src/tools.ts

11. Read a file (อ่านไฟล์โดยไม่ทำให้ Context ล้น)

read_file อ่านไฟล์ UTF-8 ถ้าเกิน 200 บรรทัด ฟังก์ชัน truncateOutput() จะเซฟไฟล์ฉบับเต็มไว้ในโฟลเดอร์ Temporary ของ OS แล้วตัดส่งเฉพาะ 200 บรรทัดท้ายสุด กลับไปให้โมเดลอ่าน เพราะข้อผิดพลาดและผลลัพธ์สำคัญมักอยู่ท้ายไฟล์

Step 12 src/tools.ts

12. Write a file (เขียนไฟล์ทั้งก้อน)

write_file ใช้ fs.mkdir(..., { recursive: true }) เพื่อสร้างโฟลเดอร์พ่อแม่ที่ยังไม่มี แล้วเขียนทับไฟล์เป้าหมายทั้งหมด ไม่มีการต่อท้ายหรือรวมไฟล์ เมื่อเขียนเสร็จจะรายงาน path และจำนวนตัวอักษรที่บันทึก

Step 13 src/tools.ts

13. Edit one exact passage (แก้ไขเฉพาะจุดที่ตรงกันเป๊ะๆ)

edit ใช้ old_string แทนการระบุเลขบรรทัด (เพราะเลขบรรทัดจะเลื่อนหลังจากการแก้ครั้งก่อนหน้า) และบังคับว่าต้องพบข้อความเดิม เพียง 1 จุดเท่านั้น หากพบ 0 จุด หรือพบมากกว่า 1 จุด จะ throw error ปฏิเสธการแก้ไขทันทีเพื่อความปลอดภัย

Step 14 src/tools.ts

14. Run a command (สั่งรัน Shell ในคอมพิวเตอร์)

run_bash รันคำสั่ง bash โดยตั้ง Timeout ไว้ที่ 30 วินาที หากคำสั่งล้มเหลว จะแปลง Exit Code และ stderr เป็นข้อความส่งกลับไปให้โมเดลอ่าน แทนที่จะโยน Error ทิ้ง เพื่อให้โมเดลสามารถวิเคราะห์และแก้ปัญหาเองต่อได้

ช่วงที่ 4: ตรรกะลูปและระบบป้องกันภัย (Steps 15 - 20)

ประกอบลูป, ป้องกัน Tool Call แหว่งจาก max_tokens, จัดการ Abort อย่างขาวสะอาด, และย่อสรุป Context

Step 15 src/agent.ts

15. Define what the agent reports (นิยามสิ่งที่ Agent รายงาน)

นิยาม AgentEvent ระดับสูง 4 แบบ: assistant_text, tool_call, tool_result, และ turn_end หน้าจอและ CLI จะรับรู้แค่ 4 เหตุการณ์นี้ โดยไม่ต้องยุ่งกับโปรโตคอล SSE อีกเลย

Step 16 src/agent.ts

16. Make the loop work (ทำให้ลูปทำงานสมบูรณ์)

เมื่อรวบรวม Tool Calls ได้ จะรันแบบเรียงตามลำดับ (Serially) ทีละคำสั่ง หากไม่พบชื่อ Tool จะสร้าง Error ผลลัพธ์ส่งให้โมเดลอ่าน แล้ววนลูปกลับไปถามโมเดลใหม่จนกว่าจะไม่มี Tool Call เหลืออยู่

Step 17 src/agent.ts

17. Never execute a truncated tool call (ห้ามรัน Tool Call ที่ถูกตัดทอนเด็ดขาด!)

กฎเหล็กความปลอดภัย: เมื่อ API ส่งเหตุผล max_tokens แปลว่าข้อความถูกตัด พารามิเตอร์ของ Tool อาจขาดครึ่ง nanopi จะ ไม่ยอมรันคำสั่งนั้นอย่างเด็ดขาด แต่จะส่งข้อความแจ้ง Error คู่กันกลับไปให้โมเดลลองใหม่ทันที

Step 18 src/agent.ts

18. Stop without leaving broken history (ยกเลิกงานโดยไม่ทิ้งประวัติที่พัง)

เมื่อตรวจพบการกด Ctrl+C (Abort) ระหว่างรัน Tools เครื่องมือที่ยังไม่ได้รันจะถูกเติมด้วยผลลัพธ์ error: aborted เพื่อให้ประวัติในสมุดโน้ตมีคู่คำสั่งและผลลัพธ์ครบสมบูรณ์ ป้องกันไม่ให้ API ครั้งต่อไปพ่น HTTP 400

Step 19 src/agent.ts

19. Treat request failure differently from abort (แยกแยะเน็ตหลุดกับการยกเลิก)

ถ้าเครือข่ายพังหรือเซิร์ฟเวอร์ตาย Agent จะบันทึกเฉพาะข้อความที่ได้รับมาก่อนหน้า และจบเทิร์นด้วยสถานะ error ทันที โดยไม่มีการ Retry แบบวนลูปไม่สิ้นสุด (Prevent infinite loop)

Step 20 src/agent.ts

20. Compact the notebook (การย่อบีบอัดสมุดโน้ตเมื่อข้อความยาวเกินไป)

เมื่อข้อความในประวัติสะสมถึง 50 ข้อความขึ้นไป ฟังก์ชัน compactContext() จะเก็บข้อความ 20 อันล่าสุดไว้เป๊ะๆ ส่วนข้อความเก่ากว่านั้นทั้งหมดจะถูกส่งไปให้โมเดลสรุปเป็นก้อนข้อความสั้นๆ ก้อนเดียว ทำให้เหลือประวัติเพียง 21 ข้อความ ป้องกัน Context Window ล้น

ช่วงที่ 5: หน้าจอ การประกอบระบบ และการเซฟประวัติ (Steps 21 - 23)

สร้าง TUI, ต่อสายทุกโมดูลเข้าด้วยกันใน cli.ts, และบันทึกลงไฟล์ session.jsonl

Step 21 src/tui.ts

21. Add the terminal user interface (สร้างหน้าจอ Terminal)

สร้างคลาส Tui ที่มีเมธอด printText(), printToolCall(), printToolResult() และจัดการสถานะ busy เพื่อไม่ให้คำสั่งใหม่ซ้อนทับงานเก่า

Step 22 src/cli.ts

22. Connect all five modules (เสียบสายเชื่อมต่อ 5 โมดูลเข้าด้วยกัน)

ใน cli.ts นำ Model, Context, builtinTools, Tui และ runAgent มาเสียบรวมกัน จัดการ AbortController รายครั้ง และใช้บล็อก switch แยกประเภท Event ส่งไปแสดงผลบนหน้าจอ

Step 23 src/cli.ts

23. Save the conversation (บันทึกบทสนทนาลง session.jsonl)

บันทึกข้อความแบบ JSON Lines (หนึ่ง Message ต่อหนึ่งบรรทัด) ลงใน ~/.nanopi/session.jsonl โดยเขียนเฉพาะส่วนใหม่ที่เพิ่มเข้ามา (Append-only) เมื่อเปิดโปรแกรมใหม่ครั้งหน้า จะโหลดประวัติเดิมกลับขึ้นมาทำงานต่อได้ทันที

🏭 Deep Dive into Production Pi (earendil-works/pi)

Inside Pi: สถาปัตยกรรมระดับ Production จริง (30 สเต็ป)

เปรียบเทียบจาก nanopi (ฉบับมินิมอลเพื่อการเรียนรู้) สู่ Pi ตัวจริง ที่ใช้งานจริงในโลกการทำงาน ซึ่งมีระบบจัดการ Session Tree, การรัน Tools แบบคู่ขนาน (Parallel Execution), การเข้าคิวเขียนไฟล์ (Write Queue), และการโหลด Skill Index

ช่วง A: เปิดเวิร์กช็อปและเตรียม Session (Steps 01 - 08)

การตรวจหากฎของโปรเจกต์ (CLAUDE.md), การลงทะเบียน Tools และสารบัญ Skills ก่อนเริ่มรับคำสั่ง

Inside Pi · Step 01 earendil-works/pi

01 · The command opens a very small door

The front door is only a few lines. It prepares the process and gives main the arguments after the Node executable and script name. It does not contain the model loop.

Inside Pi · Step 02 earendil-works/pi

02 · Prepare a session, not just a text box

The coordinator needs a working directory, model/authentication services, settings, resources, and a notebook. The SDK's session factory brings them together. If a resource loader was already supplied, this function does not reload it here.

Inside Pi · Step 03 earendil-works/pi

03 · Collect the workshop rules

These are the workshop's posted rules: project conventions, commands, and cautions. Pi walks the directory ancestry rather than scanning every child folder. Global instructions come first, then ancestor context in outer-to-inner order.

Inside Pi · Step 04 earendil-works/pi

04 · Choose what the model may ask Pi to do

The default toolbox has four tools. A tool name is not an action yet; it tells the model which actions it may request. Settings and explicit selections can change the list. Additional built-ins include grep, find, and ls.

Inside Pi · Step 05 earendil-works/pi

05 · Put the skill index on the desk

Think of a library catalog, not a stack of every book. Descriptions help the model select a skill; the location tells it where to fetch the full instructions. Discovery can inspect files without inserting all their bodies into the model's context.

Inside Pi · Step 06 earendil-works/pi

06 · Assemble the model's standing instructions

This is the coordinator's briefing sheet. The default prompt includes tool snippets and guidelines; project instructions and skill metadata are appended. A custom prompt can replace the default base.

Inside Pi · Step 07 earendil-works/pi

07 · Open the notebook at the active branch

A saved session can contain branches, settings changes, and summaries—not just chat bubbles. Pi rebuilds the conversation for the selected branch. A new session has no old conversation to restore.

Inside Pi · Step 08 earendil-works/pi

08 · Put a front desk on the same session

The same coordinator can serve a terminal UI, a program speaking RPC, or a non-interactive request. Here we follow the ordinary interactive route, not the startup-benchmark special case visible in the excerpt.

ช่วง B: รับคำสั่งและจัดเส้นทางงาน (Steps 09 - 12)

การแยกแยะ Slash Commands (/skill, /compact), การดึงเนื้อหา Skill เข้ามาใช้งานทันที

Inside Pi · Step 09 earendil-works/pi

09 · Hand the message to the coordinator

For an ordinary idle prompt, the front desk passes your text to the session and awaits the run. Interface commands can be handled earlier, and messages typed during an active run have queueing behavior.

Inside Pi · Step 10 earendil-works/pi

10 · Sort commands, ordinary text, and queued input

A slash does not always mean “replace text.” An extension command runs a registered handler; a prompt template expands text; a skill command loads instructions. An input hook may also transform or handle the message.

Inside Pi · Step 11 earendil-works/pi

11 · An explicit skill opens the book immediately

This is not the catalog path from step 05. When you explicitly invoke a known skill, Pi itself reads the file and inserts its body. The model does not first need to request a read tool call to obtain that body.

Inside Pi · Step 12 earendil-works/pi

12 · Let extensions add context before the run

Extensions are plug-ins at defined points, not a second copy of the loop. This hook can add messages and change the run's system prompt. Other hooks participate in input, context, provider requests, tool calls/results, and session events.

ช่วง C: ถาม-ทำ-ถามซ้ำ (The Production Loop: Steps 13 - 23)

การรัน runAgentLoop, Provider Adapter Matrix, Parallel Tool Execution, และ Write Queue ต่อไฟล์

Inside Pi · Step 13 earendil-works/pi

13 · Enter the loop actually used by this CLI

The session handles product concerns; Agent manages a run and its transcript state. Here it hands a snapshot, configuration, event callback, cancellation signal, and model-stream function to the loop.

Inside Pi · Step 14 earendil-works/pi

14 · Pack three things for the model

The model receives a briefing, a conversation, and a toolbox description. Pi-specific message types are converted at this boundary; they need not all look like provider messages throughout the rest of the program.

Inside Pi · Step 15 earendil-works/pi

15 · Use the selected provider, not a hardcoded vendor

The SDK supplies the loop's stream function. That function reaches the model runtime, which prepares the request and delegates to the selected provider implementation. The loop does not have to know a particular vendor's wire format.

Inside Pi · Step 16 earendil-works/pi

16 · Show progress before the reply is complete

Streaming is a sequence of events, not many separate user messages. The interface can draw text and tool-call progress while Pi maintains a partial assistant message. Finalization happens when the response ends.

Inside Pi · Step 17 earendil-works/pi

17 · Decide whether there is work to do

A reply can include both text and tool calls. Pi inspects the structured content—not whether the text happens to say “I'll read the file.” Truncated arguments are rejected even if a best-effort parser could turn them into JSON.

Inside Pi · Step 18 earendil-works/pi

18 · Decide which tool calls can run together

There is no universal “all tools always run one at a time” rule. The loop consults both its execution configuration and the tools' declarations. In the parallel path, returned transcript messages retain tool-call order even if work finishes in a different order.

Inside Pi · Step 19 earendil-works/pi

19 · Check the request before touching anything

The model proposes; the runtime checks. A valid-looking sentence is not enough: the tool must exist, its arguments must pass validation, and any before-tool policy must allow the call.

Inside Pi · Step 20 earendil-works/pi

20 · Let the tool do the physical work

This is where an enabled tool may read a file, start a shell, or change disk contents. Progress updates go back to listeners. Thrown errors are captured for the tool result; after-tool hooks can further modify the finalized result.

Inside Pi · Step 21 earendil-works/pi

21 · For a README, the tool reads bytes

If our example request leads the model to call read, this text branch gets the file contents. Offset and limit choose lines; truncation keeps a large file from swallowing the whole context budget. The tool can report how to request the next portion.

Inside Pi · Step 22 earendil-works/pi

22 · If the task edits files, writes queue per file

This is an optional branch, not something a read-only README request must do. Two same-file edits should not race just because tool calls were scheduled in parallel. The mutation queue waits for the earlier operation, then releases the next one in a finally block.

Inside Pi · Step 23 earendil-works/pi

23 · Bring the result back to the model

A tool does not normally supply the final answer by itself. It supplies evidence to the conversation, so the model can explain the README or choose another action. A tool result may be an error; that is still information the model can use.

ช่วง D: บันทึกสมุดโน้ตแบบแตกกิ่งก้าน (Steps 24 - 26)

การใช้ parentId สร้าง Message Tree และการเขียนประวัติลง JSONL อย่างปลอดภัย

Inside Pi · Step 24 earendil-works/pi

24 · Completed messages become notebook entries

Pi listens to its own events. Finalized user messages, assistant messages, and tool results can be recorded as they arrive. A stream of individual text deltas does not create a notebook line for every token.

Inside Pi · Step 25 earendil-works/pi

25 · A parent link turns the notebook into a tree

JSONL is physically a sequence of lines, but id and parentId describe a tree. The active leaf says which conversation path you are on. Appending a new message makes it a child of that leaf.

Inside Pi · Step 26 earendil-works/pi

26 · JSONL is simple storage, not a crash guarantee

The usual session location is under ~/.pi/agent/sessions/, grouped by an encoded working-directory path. This method can defer a fresh session's initial write, flush its buffered entries, or append a later entry.

ช่วง E: บีบอัด Context และเคลียร์สถานะ (Steps 27 - 30)

การเช็ก Token Limit, การสร้างข้อความสรุป, และการส่ง Settle Event เพื่อกลับสู่สถานะพร้อมรับคำสั่งใหม่

Inside Pi · Step 27 earendil-works/pi

27 · Check space at the next-response boundary

Action in code: AgentSession._compactBeforeNextAssistantResponse(). This is installed in the next-turn preparation hook. Usage-backed estimates also account for messages added after the last valid usage; without usable usage, Pi falls back to a size estimate.

Inside Pi · Step 28 earendil-works/pi

28 · Ask for a summary, not a continuation

The model should summarize the old conversation, not continue its instructions as a fresh task. Pi serializes the conversation and wraps it inside a summarization request. A tool call from the summarizer is rejected.

Inside Pi · Step 29 earendil-works/pi

29 · Send the summary plus the recent pages

Compaction changes what Pi sends next, not the fact that earlier entries existed. After successful compaction, the session records a summary and a keep boundary, then rebuilds agent messages from the selected branch.

Inside Pi · Step 30 earendil-works/pi

30 · A loop ending is not quite the same as being idle

The coordinator may still need to retry a recoverable error, compact context, or handle queued input after the low-level loop ends. It then clears temporary prompt state, flushes pending messages, and emits its settled signal. Cancellation and failures can also reach cleanup; a settled run is not automatically a successful task.

⚖️ ตัวอย่างเปรียบเทียบเชิงลึก (In-Depth Comparative Analysis)

เพื่อความเข้าใจที่กระจ่างชัด นี่คือการเปรียบเทียบ 5 มิติสำคัญที่แบ่งแยกระหว่าง "โมเดลแชททั่วไป" กับ "AI Coding Agent ตัวจริง"

COMPARISON 1

Chatbot ทั่วไป VS AI Coding Agent Loop

ความแตกต่างสำคัญที่สุดคือ "Autonomous Feedback Loop": Chatbot ทั่วไปพูดจบแล้วหยุดทันที แต่ Coding Agent จะลงมือทำ ดูผลลัพธ์ แล้วแก้ปัญหาต่อเองจนเสร็จ

💬 Chatbot ธรรมดา (เช่น ChatGPT Web)
  • Single-turn Request/Response: ผู้ใช้ถาม → AI ตอบเป็นตัวหนังสือ → จบกระบวนการ
  • ไม่มีผลต่อโลกจริง: AI แนะนำโค้ดใน Markdown แต่ผู้ใช้ต้องคัดลอกไปวางเองใน IDE
  • ไม่รู้ว่าโค้ดที่ให้รันผ่านไหม: ถ้าโค้ดพัง ผู้ใช้ต้องก๊อป Error กลับมาแปะถามใหม่รอบสอง
🤖 AI Coding Agent (เช่น nanopi, Claude Code)
  • Multi-turn Autonomous Loop: ผู้ใช้สั่ง → Agent สั่งเปิดอ่านไฟล์ → อ่านแล้วคิด → แก้ไฟล์ → รันเทสต์ → ถ้าเทสต์ตก Agent สั่งแก้ไฟล์ซ้ำจนกว่าเทสต์จะผ่าน
  • มี Side Effects จริง: สร้าง แก้ ลบไฟล์ และรัน Terminal Shell บนเครื่องได้จริง
  • ตรวจผลลัพธ์ด้วยตัวเอง: อ่าน stderr และ stdout ของ bash มาปรับแผนเองแบบ Real-time
COMPARISON 2

Pure Functions VS Impure Tools (Side Effects)

ทำไมฟังก์ชันใน tools.ts จึงเป็น Impure Functions และมีผลกระทบความปลอดภัยอย่างไร?

มิติการเปรียบเทียบ Pure Function (ฟังก์ชันบริสุทธิ์) Impure Tool ใน Agent (เครื่องมือจริง)
ผลลัพธ์เมื่อ Input เหมือนเดิม ให้ค่าเดิมเสมอ (เช่น add(2, 3) => 5) อาจให้ผลไม่เหมือนเดิม ขึ้นอยู่กับสถานะในเครื่อง (เช่น อ่านไฟล์ที่ถูกแก้ไปแล้ว)
ผลกระทบภายนอก (Side Effects) ไม่มีเลย ไม่แตะต้องฮาร์ดแวร์หรือเน็ต เขียนทับไฟล์ในฮาร์ดดิสก์, รันคำสั่ง bash ลบข้อมูล, จองหน่วยความจำ
การยกเลิก (Undo/Rollback) ไม่ต้องทำอะไร เพราะไม่ได้เปลี่ยนสเตต การกดยกเลิก (Abort) ไม่สามารถย้อนคืน การเขียนไฟล์หรือคำสั่งที่รันไปแล้วได้!
COMPARISON 3

Normal HTTP REST Response VS SSE Streaming

ทำไม llm.ts จึงต้องใช้ Server-Sent Events (SSE) และยอมรับความยุ่งยากในการรวม Chunks?

❌ ถ้าใช้ Normal HTTP Response (รอทั้งก้อน):

เมื่อโมเดลกำลังคิดคำตอบ 4,000 tokens หน้าจอจะค้างนิ่งสนิทเป็นเวลา 20-30 วินาที ผู้ใช้จะไม่รู้เลยว่าโปรแกรมค้างหรือกำลังทำงานอยู่

POST /chat -> [รอ 25 วินาที...] -> { "content": "hello world" }
✅ เมื่อใช้ SSE Streaming (แบบใน nanopi):

ตัวอักษรแรกปรากฏบนหน้าจอภายใน 400ms (Time-to-first-token ต่ำมาก) ผู้ใช้เห็นความคิดของโมเดลไหลออกมาทันที และสามารถกดยกเลิก (Ctrl+C) ได้ทันทีถ้าโมเดลเริ่มตอบออกทะเล

data: {"delta": {"content": "Hel"}}
data: {"delta": {"content": "lo "}}
data: {"delta": {"content": "World"}}
COMPARISON 4

Stateless Model VS Stateful Agent (Context Notebook)

ความจริงที่หลายคนเข้าใจผิด: ตัวโมเดล AI (LLM Server) "ไม่มีความจำเลยแม้แต่น้อย" (Stateless) ทุกคำขอที่ยิงไปที่เซิร์ฟเวอร์ มันจะลืมทุกอย่างทันทีที่ตอบเสร็จ

สิ่งที่ทำให้รู้สึกว่า Agent มีความจำต่อเนื่อง คือ สมุดโน้ต (Context) ใน nanopi:

รอบที่ 1: ส่ง [User: "แก้บั๊กใน app.ts"] -> AI ขอ [read_file "app.ts"]
รอบที่ 2: ส่ง [User: "แก้บั๊ก", Assistant: "ขออ่านไฟล์", ToolResult: "โค้ดใน app.ts"] -> AI ส่ง [edit ...]
รอบที่ 3: ส่ง [ประวัติทั้งหมด + ผลการ edit] -> AI ส่งข้อความ "แก้ไขเสร็จเรียบร้อยครับ"

ดังนั้น ถ้าสมุดโน้ตหนาเกินไป (Context Window เต็ม) จึงต้องมี Step 20: Compact the notebook เพื่อสรุปย่อประวัติเก่าๆ ไม่ให้ค่าใช้จ่าย Token พุ่งสูงจนเกินขีดจำกัด

COMPARISON 5

nanopi (Teaching Agent) VS Production Frameworks (Pi / Claude Code / Cursor)

ฟีเจอร์ / ความสามารถ nanopi (ฉบับเรียนรู้ ~900 บรรทัด) Production Agent (Pi, Claude Code, Cursor)
การรองรับค่ายโมเดล (Provider) รองรับเฉพาะ OpenAI-compatible 1 มาตรฐาน รองรับ Anthropic, Google Gemini, Ollama, Bedrock พร้อม Provider Adapter
ความปลอดภัยของคำสั่ง Shell ไม่มี Sandbox, ไม่มี Allowlist, สั่งรันได้ทุกคำสั่งของผู้ใช้ มี Confirmation Dialog, รันใน Docker/Sandbox ป้องกันลบไฟล์ระบบ
การรัน Tools พร้อมกัน รันแบบเรียงแถวทีละตัว (Serial) รันคู่ขนาน (Parallel execution) สำหรับคำสั่งที่ไม่มีผลกระทบต่อกัน เช่น อ่านหลายไฟล์พร้อมกัน
การบีบอัด Context นับจำนวน 50 ข้อความอย่างหยาบๆ นับ BPE Token จริงๆ, มี Vector Index, และรักษาคู่ Tool Call/Result ไม่ให้แตกออกจากกัน
